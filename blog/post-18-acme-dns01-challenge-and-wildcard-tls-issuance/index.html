Platform Maintenance: Automated OS Patching, Manual ACME DNS-01 Challenges, and Wildcard TLS Recovery

4 August 2026

Tags: homelab, kubernetes, maintenance, ansible, os-patching, acme, tls, cert-manager, sre, devops

As a platform matures, maintenance becomes an inevitable reality. The passage of time brings kernel updates, security vulnerabilities, and credential expirations that demand structured operational procedures. In this post, I cover two critical maintenance events: executing live, automated OS patching across all 5 k3s nodes via Ansible, and recovering from an expired Cloudflare API token through out-of-band ACME DNS-01 wildcard TLS certificate issuance.

The Setup

Infrastructure is not static. After running continuously for months, two separate maintenance requirements collided:

  1. OS Vulnerabilities and Kernel Updates: Both the Proxmox hypervisor layer and the underlying Ubuntu Linux OS on all 5 k3s nodes (k3s-server-01, 02, 03 and k3s-agent-01, 02) needed kernel updates (6.8.0-136-generic and 7.0.0-28-generic) and security patches (apt update && apt upgrade -y).
  2. Expired TLS Certificate: HTTPS endpoints (*.lab.ls0775.com) began showing SSL expiry warnings because cert-manager's automatic renewal stalled due to an expired Cloudflare API token.

What I Built

Part 1: Automated OS Patching & Playbook Hardening

To patch the node operating systems without risking cluster downtime:

  1. Ansible OS Patching Playbook Execution: Ran config/playbooks/os-patching-k3s.yaml to perform serial cordoning, package upgrading, rebooting, and node uncordoning one node at a time.
  2. Playbook Retry Hardening: During execution, API server reconnect pauses caused transient connection failures while waiting for nodes to return to Ready status. I updated the playbook's kubectl wait task with retry logic (retries: 30, delay: 10):
- name: Wait for node to be Ready again
  command: >
    kubectl wait --for=condition=Ready node/{{ inventory_hostname }} --timeout=300s
  register: wait_result
  until: wait_result.rc == 0
  retries: 30
  delay: 10
  1. Hypervisor & Cluster Verification: All 5 k3s nodes and Proxmox compute hosts were successfully patched, rebooted, and verified Ready.

Part 2: Out-of-Band ACME DNS-01 Challenge & Wildcard TLS Issuance

  1. Root Cause Identified: Discovered that the Cloudflare API Token (cfut_1ARK...) stored in Key Vault had expired on Cloudflare's servers. Cert-manager's pre-flight zone lookup failed, causing cert-manager to re-queue orders indefinitely without reaching Let's Encrypt.
  2. Direct ACME Client Execution: Using the cluster ACME account key (letsencrypt-prod-account-key), I initialized a direct ACME Order against Let's Encrypt production endpoints.
  3. DNS TXT Record Challenge: Extracted SHA-256 challenge hashes (bzD4z0Q... & hlBQ7_CV...) and published _acme-challenge TXT records to Cloudflare DNS.
  4. Certificate Issuance & Distribution: Let's Encrypt validated the records and issued a fresh 90-day wildcard certificate (*.lab.ls0775.com / lab.ls0775.com, valid Aug 4, 2026 – Nov 2, 2026). I updated the lab-wildcard-tls secret across all active namespaces (cert-manager, argocd, default, headlamp, homepage, monitoring, storage, and cattle-system).
  5. Ingress Reload: Restarted Traefik in kube-system, restoring HTTP/2 200 HTTPS connectivity across all lab web applications.

The Decision

When maintenance needs arise, automation must be balanced with operational agility:

  • For OS Patching: Use Ansible automation with serial node draining to ensure that patching a 5-node cluster requires zero manual SSH commands while preserving etcd quorum.
  • For Credential Expiration Outages: Execute out-of-band ACME challenges directly against the CA to restore platform UIs immediately, rather than waiting for multi-layer credential pipeline reconciliation.

What Went Wrong

  • Transient API Reconnect Pauses: When control plane nodes reboot during OS patching, local kubectl connections momentarily drop. Adding retry loops to Ansible tasks prevents the playbook from failing prematurely during standard node reboots.
  • Multi-Namespace Secret Sync: Wildcard TLS certificates must be distributed to every namespace using ingress resources. Some services (e.g. Rancher) require explicit secret key mappings (tls-rancher-ingress) to pick up renewed certificates cleanly.

What This Taught Me

  • Maintenance is a Routine SRE Discipline: Regular OS patching and certificate lifecycle management are just as vital to platform health as shipping new workloads.
  • Automated Playbooks Require Resilience: Infrastructure automation must account for transient network disconnects during node reboots.
