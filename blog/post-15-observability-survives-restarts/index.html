Making Observability Survive Restarts: Loki S3, Persistent Metrics, and the Fixes That Followed

27 May 2026

Tags: homelab, observability, loki, minio, prometheus, grafana, argocd, kubernetes, sre

In Post 10, I was explicit about the biggest gap in the monitoring stack: Prometheus could tell me what was happening right now, but it could not tell me what had happened before a restart. That gap stopped being theoretical the moment I started treating the platform like something that should survive upgrades, pod churn, and real operational mistakes.

This post is about closing part of that gap properly. Not by adding another dashboard, but by making the observability stack durable: logs that survive pod restarts, metrics that survive pod restarts, alert history that survives pod restarts — and the unexpected breakages that surfaced as soon as I touched the stack.

The Durability Gap Inside "Working" Observability

The observability stack was already useful:

  • Prometheus was scraping the cluster
  • Grafana was visualizing it
  • Alertmanager was routing alerts
  • Loki existed as a direction of travel

But useful is not the same as durable.

At that point:

  • Prometheus had no persistent volume, so a restart meant losing metrics history
  • Alertmanager had no persistent volume, so silences and notification state disappeared on restart
  • Loki was still effectively ephemeral, which meant log history vanished with the pod

That is fine for a demo. It is not fine if the point of the platform is learning operational behaviour that looks like production. If a monitoring stack forgets everything every time a pod restarts, it cannot help with post-mortems. It can only help with live staring at graphs.

What I Changed

The fix split into three parts.

1. Prometheus got durable storage

Prometheus now uses a 10Gi PVC via local-path:

prometheus:
  prometheusSpec:
    storageSpec:
      volumeClaimTemplate:
        spec:
          storageClassName: local-path
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              storage: 10Gi

That is not cross-node HA storage. It is a simpler and more immediate improvement: metrics survive pod restarts on the same node, which is a massive step up from "everything disappears if the pod is rescheduled."

2. Alertmanager got durable storage

Alertmanager got the same treatment, with a smaller 1Gi PVC. That means silences, deduplication state, and alerting context now survive restarts instead of resetting at the worst possible moment.

This is one of those changes that sounds minor until you imagine debugging a noisy alert storm and losing all silences because the pod restarted mid-incident.

3. Loki moved from ephemeral storage to MinIO S3

This was the bigger change.

Instead of storing data on the pod filesystem, Loki now writes to MinIO over the in-cluster S3 API:

loki:
  schemaConfig:
    configs:
      - from: "2026-05-03"
        store: tsdb
        object_store: s3
  storage:
    type: s3
    bucketNames:
      chunks: loki
      ruler: loki
      admin: loki
    s3:
      endpoint: http://minio.storage.svc.cluster.local:9000

Credentials come from a Kubernetes Secret via environment variables rather than being committed to the repo. The result is that log history survives Loki pod restarts, and MinIO becomes the durable backing store for the logging layer.

That matters because logs are often only interesting after something has already broken.

The Part That Wasn't Obvious

The Loki migration was not a one-shot config change. It took three iterations to make it actually work.

Loki still needed local scratch space

My first instinct was: if the backend is S3, local storage should be unnecessary. That turned out to be wrong. Loki still needs writable local space for its WAL and temporary files, so emptyDir had to stay mounted at /var/loki even after the durable storage moved to MinIO.

That is a useful distinction:

  • Durable data path: MinIO S3
  • Ephemeral working space: emptyDir at /var/loki

If you remove the second one, the first one does not save you.

Loki would not expand environment variables by default

The access key and secret key were injected through secretKeyRef, but Loki does not automatically substitute ${ENV_VAR} placeholders in the config. The fix was adding:

singleBinary:
  extraArgs:
    - -config.expand-env=true

Without that, the config looked right in Git and was wrong at runtime.

An old schema entry kept sending data to the wrong place

The legacy filesystem schema entry from 2024-04-01 was still present. That meant current-time data was still being routed toward the old filesystem store instead of the new S3 backend. The fix was to remove the old entry and leave a single S3-backed schema from 2026-05-03.

This is the kind of bug that is easy to miss because the configuration is syntactically valid. It is just not doing what you think.

What Broke While I Was Fixing It

This is the part I like documenting most, because it is the most realistic.

Changing one part of a platform often surfaces assumptions somewhere else. In this case, making the observability stack more durable exposed two unrelated stability issues.

Grafana crashed on startup after the chart upgrade

As part of the monitoring work, kube-prometheus-stack moved from 84.1.2 to 84.5.0. After the upgrade, Grafana's init-chown-data init container started failing with Permission denied against existing PVC directories like png, pdf, and csv.

The PVC contents already had the correct ownership. The init container was trying to "fix" a problem that did not actually exist, and in doing so, it created a real one. The resolution was:

grafana:
  initChownData:
    enabled: false

That is a good reminder that chart defaults are not universally safe once a workload has real, existing state.

Argo CD repo-server had been unhealthy for days

This one was pre-existing, which made it even more interesting. The Argo CD repo-server had been stuck in repeated restarts because its liveness probe was too strict:

  • the liveness path was /healthz?full=true
  • the full check included Git connectivity
  • the timeout was 1 second

That was not enough. The process was healthy, but the probe budget was unrealistic. The fix was simply to give the probes enough time:

repoServer:
  livenessProbe:
    timeoutSeconds: 10
  readinessProbe:
    timeoutSeconds: 10

The handoff notes recorded 1807 restarts over 3 days before this was corrected. That is exactly the kind of problem observability work is supposed to reveal: not just new features, but broken assumptions already sitting in the platform.

The Real Decision: Durability First, Availability Later

The most important architectural point in this change is that I did not solve every reliability problem at once.

Prometheus and Alertmanager now persist to local-path. Loki persists to MinIO. That means the stack is much better at surviving pod restarts and routine churn. It does not yet mean the entire observability stack cleanly survives loss of a workload node.

That distinction matters.

This work was about durability:

  • keeping logs after Loki restarts
  • keeping metrics after Prometheus restarts
  • keeping alert state after Alertmanager restarts

The next layer is availability under host loss, which is a different problem entirely. Shared storage, replica placement, workload spread, and node-failure behaviour belong to that conversation. In this repository, that work is now tracked separately instead of being hand-waved together with "persistent storage."

This was the right trade-off. Solving one reliability dimension cleanly is better than pretending to solve three at once with vague language.

What This Taught Me

The first lesson is that persistence and availability are not synonyms. A PVC is not high availability. S3-backed logs are not automatic failover. Durable state is one layer of reliability, and it is still worth doing even when the broader HA story is unfinished.

The second lesson is that operational improvements often arrive as a bundle: the intended change, the side effects of that change, and the unrelated problems you finally notice because you were looking closely. That is normal platform work. You touch logging storage and end up fixing Grafana startup behaviour and an Argo CD probe budget that had been wrong for days.

That is also why this kind of work is worth writing about. The interesting part is not "I added a PVC." The interesting part is learning how systems actually behave once they have state, upgrades, and history.

What's Next

The observability stack now remembers more of what happened, which makes it much more useful in the real world. The next reliability question is broader: not "does this survive a pod restart?" but "what happens when an entire workload host disappears?" That host-loss survivability work is the next platform gap to close.
