The Control Node is Infrastructure Too

23 May 2026

Tags: homelab, ansible, devops, workstation, kubectl, k3s, wsl, configuration-management

Every server in this homelab is defined by code. The k3s nodes have Ansible playbooks. The Proxmox VMs have OpenTofu configuration. But the machine running all of those tools — the workstation — had nothing. Its state was entirely undocumented: tools installed by hand over time, repos added ad hoc, no record of what was needed or why. If I had to rebuild it, I'd spend hours figuring out what belonged on it. This post is about fixing that.

The Control Node Pattern

In enterprise environments, IaC and configuration management run from a designated control node — a CI/CD runner, a bastion host, or a developer workstation. The control node is not a managed node. It is the operator plane: the machine from which all infrastructure is managed.

ADR-013 established this pattern for the homelab: OpenTofu and Ansible run exclusively from the engineer's workstation. Infrastructure nodes (pve01, pve02, k3s nodes) must not have the homelab repo cloned or IaC tooling installed. The reasons:

  • Separation of concerns: The tool that provisions infrastructure should not run on the infrastructure it manages. If pve01 is lost, the ability to rebuild it must not be lost with it.
  • Blast radius: A mistake on an infrastructure node — wrong tofu destroy, misconfigured credentials — can cascade into the cluster it's managing. Running from a workstation contains that blast radius.
  • Audit trail: All applies and playbook runs come from one place, with one identity, traceable to one operator.

What ADR-013 didn't originally address: the workstation itself needs the same documentation discipline as the nodes it manages. If the toolchain isn't codified, the control node is a single point of failure with no recovery playbook.

What Belongs on a Control Node

The workstation needs a specific set of tools to manage this stack:

Tool Purpose Source
ansible Configuration management of all nodes apt install ansible
kubectl k3s cluster operations Kubernetes apt repo (pkgs.k8s.io)
helm Chart management for k3s workloads Buildkite helm apt repo
tofu Proxmox VM provisioning OpenTofu apt repo
k9s Terminal UI for cluster operations GitHub binary release
gh GitHub CLI for repo workflow GitHub CLI apt repo
gitleaks Pre-commit secrets scanning Ubuntu universe
git, curl, gnupg Baseline tooling Ubuntu default repos

A few things worth noting about this list:

kubectl comes from pkgs.k8s.io — the standard Kubernetes package repository. This is the correct place to get it even though the cluster is k3s, not k8s. kubectl is a client binary; it's identical whether your cluster is k3s, EKS, or bare kubeadm. The k3s nodes themselves use the kubectl symlink bundled by k3s at /usr/local/bin/kubectl — nothing from pkgs.k8s.io is installed on them.

kubectl is pinned to the cluster minor version (v1.34 to match k3s v1.34.6+k3s1). The Kubernetes client/server skew policy supports one minor version in either direction, but pinning avoids subtle incompatibilities and makes the intent explicit. When the cluster is upgraded, the variable gets bumped.

k9s has no apt repo — it's distributed as a binary on GitHub releases. The playbook handles this with an idempotency check: compare the installed version string against the pinned version variable, download and extract only if they don't match. Bumping the version variable and re-running the playbook upgrades it.

The Bootstrap Playbook

The control node is added to the Ansible inventory as a group:

control_node:
  hosts:
    localhost:
      ansible_connection: local

ansible_connection: local tells Ansible not to SSH — it runs tasks directly on the local machine. The playbook targets this group:

- name: Bootstrap control node
  hosts: control_node
  connection: local
  become: true
  vars:
    kubectl_version: "v1.34"
    k9s_version: "v0.50.18"
  tasks:
    ...

The chicken-and-egg problem: you need Ansible to run the playbook, but the playbook installs Ansible. The solution is one manual command documented in the README:

sudo apt install ansible && sudo ansible-playbook playbooks/control-node.yaml

After that, re-running the playbook is idempotent. The second run shows changed=0 for everything except any tools that have been version-bumped.

The WSL Consideration

The control node is Ubuntu 24.04 running as a WSL2 distribution on Windows. WSL is a legitimate and increasingly common environment for DevOps work — it gives a full Linux toolchain on a Windows machine without a dedicated Linux box.

One quirk: become: true with --ask-become-pass doesn't work well when Ansible runs on localhost in WSL. Ansible's sudo prompt handshake depends on PTY behaviour that WSL's terminal layer doesn't reliably support, causing the become authentication to time out.

The fix is straightforward: run the control node playbook with sudo directly, which means Ansible already runs as root and become: true tasks escalate from root to root without any password prompt:

sudo ansible-playbook playbooks/control-node.yaml

This is a local machine — running as root is no different from running with sudo. The servers don't have this issue because they have passwordless sudo configured via cloud-init, so become: true works without prompting.

Migrating from Fedora to Ubuntu WSL

The previous control node was a Fedora workstation. The toolchain — kubectl, helm, k3s cluster access — was set up there over time without documentation. The WSL migration was an opportunity to codify everything.

The only state that needed copying was the kubectl access credentials: the x509 client certificate, private key, and CA certificate in ~/.kube/certs/. These are user credentials, not machine credentials — the certificate identifies ls0775 with group membership k3s-admins, and it works from any machine with network access to the cluster API.

# Copy certs from Fedora to WSL
scp ls0775@fedora:~/.kube/certs/ls0775.key  ~/.kube/certs/
scp ls0775@fedora:~/.kube/certs/ls0775.crt  ~/.kube/certs/
scp ls0775@fedora:~/.kube/certs/ca.crt      ~/.kube/certs/
scp ls0775@fedora:~/.kube/config            ~/.kube/config
chmod 600 ~/.kube/certs/ls0775.key ~/.kube/config

The playbook creates ~/.kube/ and ~/.kube/certs/ with mode: 0700 before the kubeconfig steps are needed. This is the extent of what Ansible can automate here — the kubeconfig itself involves certificates signed by the k3s CA and is documented as a manual procedure in docs/operations/k3s-access.md.

After copying:

$ kubectl get nodes
NAME            STATUS   ROLES                  AGE
k3s-server-01   Ready    control-plane,etcd     23d
k3s-server-02   Ready    control-plane,etcd     7d
k3s-server-03   Ready    control-plane,etcd     4d
k3s-agent-01    Ready    <none>                 22d
k3s-agent-02    Ready    <none>                 7d

$ kubectl auth whoami
Username: ls0775
Groups:   [k3s-admins system:authenticated]

The WSL workstation is now a fully functional control node, with the same cluster access as the Fedora machine — and unlike the Fedora machine, its entire setup is reproducible from one playbook.

What This Taught Me

The instinct when building infrastructure tooling is to focus on the servers. The workstation is where you work, not what you manage — it doesn't feel like infrastructure. That's wrong.

A workstation with an undocumented toolchain is a single point of failure. If it's lost, rebuilt, or replaced (as happened here, moving from Fedora to WSL), you spend time reconstructing it from memory and tribal knowledge instead of running a playbook. Every hour spent on recovery is an hour not spent on the actual work.

The control node playbook also serves as documentation. A new engineer joining the project runs one command and has a working environment. An employer reviewing the repo sees that operational discipline extends to the development environment, not just the production cluster.
