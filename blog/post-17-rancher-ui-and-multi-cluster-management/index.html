Visualizing the Platform: Deploying Rancher UI with Multi-Host High Availability

11 June 2026

Tags: homelab, kubernetes, rancher, high-availability, helm, ingress, sre, devops

When your Kubernetes cluster reaches a certain size, command-line inspection via kubectl and k9s remains indispensable, but visual platform management adds immense value — especially for multi-cluster oversight and rapid workload troubleshooting. In this post, I detail why and how I deployed Rancher Server to the k3s cluster, adhering strictly to our host-loss survivability standard (R-011) with a 2-replica high-availability configuration across physical hypervisors.

The Setup

Following our deployment of Headlamp (Post 14) for lightweight, developer-focused cluster inspection, the platform lacked an enterprise-grade control plane manager capable of multi-cluster management, cluster lifecycle tracking, and RBAC governance.

While Headlamp serves as a fantastic lightweight UI, Rancher provides a full-featured management engine — managing workloads, namespaces, secrets, and underlying nodes under a single interface. However, running an enterprise manager like Rancher on a 2-node Proxmox HA cluster requires careful design so that taking down a single host does not bring down your management UI.

What I Built

I installed Rancher Server into a dedicated cattle-system namespace using the rancher-stable Helm chart repository.

Key details of the deployment:

  1. Namespace Provisioning: Created cattle-system as the target namespace.
  2. Helm Configuration: Configured Rancher with replicas: 2 and explicit topology spread constraints (topology.kubernetes.io/zone) to ensure the two pods land across separate Proxmox hosts (pve01 and pve02).
  3. Ingress & TLS Binding: Mapped the existing wildcard TLS certificate secret lab-wildcard-tls into cattle-system as tls-rancher-ingress to serve secure traffic at https://rancher.lab.ls0775.com.
  4. Dashboard Integration: Added a Rancher service tile to the Homepage observability section so it sits right alongside Grafana, Headlamp, and Argo CD.

The Decision

The core architectural choice is documented in ADR-020: Rancher Cluster Management UI.

Rather than running Rancher as a single replica (which would violate our R-011 Workload Availability Standard), I selected a 2-replica Stateful deployment with anti-affinity:

replicas: 2
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: rancher

Because pve01 and pve02 are labeled as distinct failure domain zones, Kubernetes forces the two Rancher pods onto separate physical hypervisors. If pve01 undergoes physical maintenance or fails, pve02 maintains full access to the Rancher interface without interruption.

What Went Wrong

During the initial deployment, Rancher stuck in a pending state with TLS handshake errors.

The root cause was two-fold:

  1. Cert-Manager Hook Mismatch: Rancher by default attempts to issue its own internal TLS certificates via cert-manager if ingress.tls.source is omitted. Because we rely on a pre-issued wildcard cert (lab-wildcard-tls), Rancher's internal issuer conflicted with the existing ingress settings. Specifying ingress.tls.source=secret resolved the hook loop.
  2. Local DNS Override Needed: Once deployed, accessing rancher.lab.ls0775.com timed out externally until a local DNS override pointing to the MetalLB LoadBalancer VIP (192.168.99.100) was configured in the UniFi gateway.

What This Taught Me

  • Management UIs Should Follow the Same HA Standards as Applications: It is easy to treat administrative UIs as "secondary tools" and deploy them as single-replica workloads. However, when an outage occurs, your management UI is the exact tool you need to diagnose the failure — meaning it must be as resilient as your production workloads.
  • Failover Domains Must Be Explicit: Declaring topology.kubernetes.io/zone on hypervisor nodes allows Kubernetes schedulers to make host-aware decisions without needing expensive cloud APIs.
