Zero-Downtime Maintenance: Serial Proxmox Drains and Asymmetric RAM Upgrades

5 August 2026

Tags: homelab, proxmox, kubernetes, hardware, maintenance, memory, sre, devops

Hardware upgrades on bare-metal infrastructure usually mean scheduled downtime. But when your platform is designed with failure-domain awareness and multi-node HA, physical host maintenance becomes a routine operational task. In this post, I detail how I performed serial maintenance shutdowns of both Proxmox hypervisors (pve02 and pve01), upgraded system memory using asymmetric SODIMM modules, performed a full NVMe disk audit, and restored cluster state — all while keeping our SSoT documentation fully synchronized.

The Setup

Our Proxmox HA cluster consists of two main compute nodes (pve01 and pve02) and a third Synology-backed QDevice (pve03). The k3s Kubernetes cluster spans these hypervisors with 3 control plane nodes and 2 worker nodes.

The goal for this session was twofold:

  1. Repurpose hardware compute nodes to Intel NUC 7 i7 hosts (NUC7i7BNH with Core i7-7567U CPUs).
  2. Upgrade memory to 24GB DDR4 RAM per node using asymmetric SO-DIMM configurations (1x 16GB + 1x 8GB).

What I Built

Following our standard procedure docs/operations/procedures/proxmox-single-host-maintenance-shutdown.md:

  1. Serial Host Drain 1 (pve02):
    • Cordoned worker node k3s-agent-02 and control plane node k3s-server-02.
    • Evicted running workloads onto pve01.
    • Gracefully shut down VMs 304 and 305.
    • Executed systemctl poweroff on pve02.
    • Verified that pvecluster01 maintained quorum (2/3 votes via pve01 + QDevice).
  2. Host Recovery & Uncordon: Powered pve02 back on, verified VM restart, uncordoned k3s-server-02 and k3s-agent-02, and confirmed Ready node status.
  3. Serial Host Drain 2 (pve01 & RAM Upgrade):
    • Cordoned worker node k3s-agent-01 and control plane node k3s-server-01.
    • Drained workloads onto pve02.
    • Shut down VMs 301 and 302, then powered off pve01.
    • Installed the upgraded memory module.
    • Powered pve01 back on and verified free -h returning 23Gi recognized system RAM.
  4. Live Block Device Scan: Executed live lsblk audits across both hypervisors:
    • pve01: Kingston SNV2S500G 465.8GB NVMe SSD
    • pve02: Samsung 960 PRO 476.9GB NVMe SSD
  5. SSoT Documentation Synchronization (ADR-014): Updated canonical specs in docs/environment-data.md and logged the operational record in docs/operations/handoff-log.md.

The Decision

Asymmetric RAM (Intel Flex Memory Technology)

When upgrading RAM from 16GB to 24GB using one 16GB SODIMM and one 8GB SODIMM, a common question arises: Will asymmetric memory work reliably on an Intel NUC?

The answer is yes, thanks to Intel Flex Memory Technology:

  • The first 16GB (8GB from the 16GB module + 8GB from the 8GB module) operates in Dual-Channel Mode for maximum memory bandwidth.
  • The remaining 8GB on the 16GB module operates in Single-Channel Mode.

This provides the optimal balance of cost, performance, and capacity without needing matched 16GB pairs.

What Went Wrong

During the drain of k3s-agent-01, kubectl drain hit a 10-minute timeout waiting for background controller pods (such as argocd-server and loki-gateway) to confirm termination.

The cause was a transient API server connection timeout while etcd re-elected a leader between control plane nodes. Rerunning kubectl drain with --force --grace-period=0 evicted the remaining pods instantly and allowed the VM shutdown to proceed cleanly.

What This Taught Me

  • Serial Maintenance Preserves Quorum: Taking down hosts one at a time ensures that both Corosync (Proxmox) and Raft/etcd (Kubernetes) remain quorate throughout the operation.
  • SSoT Maintenance Prevents Documentation Drift: Updating hardware facts in docs/environment-data.md immediately after physical hardware changes prevents future SRE confusion and keeps AI agent context clean.
