Where Are Your Passwords? A Credential Audit and the Secret Management Gap

30 May 2026

Tags: homelab, security, kubernetes, azure, secrets, etcd, sre, devops

Every platform has a credentials problem hiding somewhere. Mine was hiding in plain sight: there was no vault, no external secret store, and one service had its admin password committed directly to a Git repository in plaintext. This post is about finding all of that, deciding what to do about it, hitting a wall trying to do it, and understanding why the situation was less catastrophic than it first appeared.

The Question That Started It

The prompt was simple: "I do not seem to have any vault or similar service to store usernames and passwords. On any outage to the service the changed password is lost."

That is a good instinct. If you change a password inside an application, and the cluster dies before the change is backed up, what happens? The answer depends entirely on how your secrets are managed — and in my case, the answer was "we'll figure it out when it happens," which is not a posture I wanted to keep.

So I did a full credential audit.

What the Audit Found

Kubernetes Secrets live in etcd. They are not stored in Git, they are not in a vault, and they are not in any external system. They exist only inside the cluster. The four secrets that were applied manually with no external record:

Secret Namespace Risk
minio-root-credentials storage Lost on rebuild
loki-minio-credentials monitoring Lost on rebuild
cloudflare-api-token cert-manager Lost on rebuild
tofu-state-user-credentials storage Lost on rebuild — and re-opens the IaC state risk

That last one mattered more than it appeared. The whole point of migrating OpenTofu state to MinIO (Post 12) was to have a recoverable remote backend. But tofu-state-user-credentials is the key that unlocks that backend. If it disappears because the cluster is rebuilt, OpenTofu cannot reach its own state file — and the R-002 mitigation I spent an entire session on starts unravelling.

Then there was the one I was not expecting.

grafana:
  adminPassword: admin

That line was committed to k8s/apps/monitoring/kube-prometheus-stack-values.yaml. A plaintext password — weak, default, and in version control. Two problems at once: the value was wrong, and the location was wrong.

Deciding What to Do About It

Three options emerged, each with a different trade-off.

Option A: SOPS + Age

Encrypt secret manifests and commit the ciphertext to Git. An Age private key decrypts them. Cluster rebuild means: apply the key, re-apply the manifests, done.

The problem is that the Age key is now the single point of failure. You have moved the bootstrap problem, not eliminated it. You also need to update a Git file every time you rotate a secret, which makes rotation slightly more friction-filled than it should be.

Option B: Sealed Secrets

Bitnami Sealed Secrets encrypts secrets with the cluster's own key and commits SealedSecret CRDs to Git. The controller decrypts them at runtime.

Same problem as SOPS: if the cluster is destroyed, the controller key needs to be backed up separately. It also does not give you an external source of truth — you have a cluster-internal key managing cluster-internal secrets, and the key needs its own backup strategy.

Option C: Azure Key Vault + External Secrets Operator

Store secrets in Azure Key Vault. The External Secrets Operator (ESO) runs in the cluster, authenticates to Key Vault with a Service Principal, and materialises standard Kubernetes Secrets from Key Vault values on a refresh schedule.

The clear advantage: the secrets actually live somewhere external. Cluster rebuild means: apply the one bootstrap SP credential, re-apply the ESO manifests, and ESO fetches everything else automatically from Azure. Rotation happens in the Key Vault UI and propagates to the cluster on the next sync cycle without touching Git at all.

For the learning goals of this project — building habits that transfer to enterprise Kubernetes environments — Azure Key Vault + ESO is also the closest approximation of how production platforms actually handle this problem. It made sense as the right direction.

That is the decision I recorded in ADR-019.

The Part That Did Not Work

I had az login working, the resource group existed, and I created the Key Vault:

az keyvault create \
  --name kv-homelab-ls0775 \
  --resource-group rg-homelab \
  --location australiaeast \
  --enable-rbac-authorization true

Then it stalled in two places. Creating a Service Principal requires Azure AD app registration permissions, and my Visual Studio Enterprise subscription account does not have them. Writing secrets to the Key Vault after creating it also failed — creating the vault with RBAC mode enabled means you need a role assignment before you can write to it, and assigning roles requires the same Graph API permissions I did not have.

ERROR: Insufficient privileges to complete the operation.

This is a known constraint with personal Microsoft Account subscriptions. The fix is to request those permissions from an Azure AD admin, or to create the Service Principal through the Azure Portal directly. In my case, this work is deferred until that is sorted. The Key Vault exists and is empty. The ESO manifests are in Git and ready to apply. The gap is a permissions problem, not an architecture problem.

Wait — Do I Actually Have a Recovery Path Already?

Before writing off the situation entirely, I asked an important question: I run 6-hourly etcd backups. Does that change things?

Yes, it does.

Kubernetes Secrets are stored in etcd. Every etcd snapshot includes them. On a full cluster rebuild with a successful restore from snapshot, all four of those manually applied secrets come back exactly as they were. The maximum data loss window is 6 hours — the interval between backups.

That changed the risk assessment significantly. The original concern was "secrets lost with no recovery path." With 6-hourly backups, the correct description is "secrets recoverable from the most recent snapshot, with up to 6 hours of potential loss." That is not the same thing as no recovery path.

The residual risk is a different question: where do the backups live?

In my case, the etcd snapshots go to Synology NFS — which is on-site. R-003, the open risk for on-site-only backups, now overlaps with R-012. A house-level event (fire, power surge) could take out both the cluster and the backups together. That connection was worth making explicit in the risk register, because the two risks reinforce each other in a way that was not previously documented.

The Distinction That Matters

This session reinforced something I keep returning to in this series: durability and availability are not the same as recoverability from total loss.

The observability stack changes in Post 15 made monitoring durable — able to survive pod restarts. The etcd backups make the cluster's secret state recoverable — restorable after full loss. Neither of those is the same as having an external source of truth that exists independently of the cluster. etcd backups are a recovery mechanism. A vault is a source of truth. Both are useful. They are not substitutes for each other.

The Immediate Fix

While the vault work is deferred, the plaintext password was fixable immediately and independently.

The kube-prometheus-stack Helm chart supports referencing an existing Kubernetes Secret instead of accepting a password in the values file:

grafana:
  admin:
    existingSecret: grafana-admin-credentials
    userKey: admin-user
    passwordKey: admin-password

I created grafana-admin-credentials in the monitoring namespace with a strong generated password, removed the plaintext line from the values file, and upgraded the Helm release. Grafana rolled out with the new configuration and the old plaintext value is gone from the repository.

This is the minimum bar: no credentials in Git, even weak defaults. The secret is still only in etcd — which is covered by the 6-hourly backup — but it is not in version control.

What This Taught Me

The most useful thing this session produced was not the Key Vault or the ESO manifests (neither of which is running yet). It was the audit itself.

I did not know exactly which secrets were manually applied and had no external record until I listed them out, looked at what was in the cluster, and thought through what happens on a rebuild. That exercise produced a clear picture of the risk surface in about ten minutes. Every platform should do this periodically. The secrets problem is never as bad as you fear or as safe as you assume — but you do not know which until you look.

The second lesson is about permissions. Azure Key Vault is the right architecture. The implementation is blocked by a permissions constraint that has nothing to do with the architecture. That is a real production pattern: the right answer is sometimes available only after clearing access-control gates that sit outside the technical domain. The correct response is to do the architecture work, document the decision, and wait for the gate to open — not to compromise on the approach because the gate is annoying.

What's Next

The Key Vault sits empty in australiaeast, ready to be populated when Azure AD permissions are in order. The ESO Helm chart values and ClusterSecretStore are committed to Git. The deployment itself is a Helm install and three kubectl apply commands once the Service Principal exists.

In the meantime, the bigger open risk is R-003: the etcd backups that provide the current recovery path live entirely on-site. That gap connects to both secret durability and general disaster recovery. The next meaningful improvement to platform resilience is getting those backups off-site.
